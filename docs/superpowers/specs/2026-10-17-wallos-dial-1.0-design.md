# Wallos Dial 1.0 design

**Status:** architecture approved in conversation; written specification awaiting Luke's review.

**Target release:** Dial `1.0.0`, based on the reviewed Wallos `5.8.3` image.

**Product boundary:** a pinned Docker source overlay for Wallos, with a desktop-first interface. It is not a native Wallos theme plug-in.

## Intent and release bar

Dial 1.0 should be useful to a person with their own subscription ledger, rather than only looking complete with the maintainer's data. They must be able to choose or supply a sharp icon for a subscription, adjust its presentation, and organize categories without editing PHP, Docker mounts, or SQLite by hand. Existing Wallos features and account data must survive installation and rollback. The public package must contain no maintainer-specific SVG, uploaded Logo, account mapping, database, credential, or host configuration.

The release bar includes a fresh installation, a migration from Dial 0.1.1 on a copy of an existing database, a tested rollback, authenticated browser flows, and a public image for `linux/amd64` and `linux/arm64`. The release documentation will state the exact tested Wallos version. New upstream Wallos releases still require review and a new Dial build; the version pin and compatibility hash check remain.

## Chosen approach and alternatives

The chosen approach keeps `subscriptions.logo` and the user's original upload intact. A Dial-owned table stores each subscription's optional icon selection and presentation. A shared resolver supplies the same result to the dashboard, subscription list, details, and any summary that displays a service icon. Wallos's `categories` table remains the single category store, with a dedicated Dial manager and hardened category endpoints.

Replacing `subscriptions.logo` directly would touch fewer renderers but discard a reliable way to restore the original image. Continuing the existing filename-to-SVG PHP map would keep private installations working but still require manual file and Compose edits for every new user. The map remains a legacy fallback; the new UI is the primary path.

## Public icon catalog and private assets

The public catalog has nine service-icon candidates: `apple-one`, `chatgpt`, `claude`, `jianying`, `netcup`, `nmcloud`, `proxy-seller`, `racknerd`, and `vmiss`. These are service identifiers, not endorsements or claims that the designs are official. The Apple candidate uses an Apple silhouette; its provenance must be described accurately. Three silhouettes came from Simple Icons v16; the other six were drawn in the local vector-generation script. Each asset gets a source, license and trademark note, and an optical-size value in the catalog manifest before release. [Simple Icons' own disclaimer](https://github.com/simple-icons/simple-icons/blob/develop/DISCLAIMER.md) says its CC0 package license does not establish the rights of each brand mark, so each candidate must receive an individual source/mark review. A candidate that cannot pass is resolved with Luke before the release, not silently shipped or removed.

Seven SVGs representing Luke's own brands or domains, their generation definitions, original upload filenames, and the private filename map are excluded from Git, Docker build context, GHCR images, docs assets, fixtures, and release archives. Screenshots use fictional data and may show only the reviewed public catalog. The package check uses an explicit public allow-list and private-asset deny-list without treating the already public Demo domain as a private asset. It continues to reject databases, secrets, and local mapping files. The existing optional local map remains supported for private installations and takes effect only when no explicit icon preference has been saved.

Bundled icons are static, validated SVGs under a new `images/dial-catalog/` path. The old `images/dial-logos/` path remains for optional private mounts; this avoids a user's existing volume mount hiding the new catalog. Their glyphs sit inside a common square box with per-icon optical calibration, so a wide or dense mark does not appear larger than its neighbors. The subscription name remains visible beside the mark. A missing catalog key falls back to the original Logo without a broken image.

## User-facing icon flow

The add and edit subscription forms have an Icon control with four choices: use the existing Logo, use a built-in service icon, choose from My Icons, or upload a new icon to My Icons. Cards also have a Change icon action. The chooser previews the actual size against the warm-white card surface before saving. It works with mouse and keyboard, exposes focus and selected states, and has English, Simplified Chinese, and Traditional Chinese labels.

For each subscription the user can select a plain or framed presentation, original color or monochrome treatment, and a bounded visual-size adjustment of 80–120%. The default is optically calibrated and requires no adjustment. These are presentation choices only; no arbitrary CSS or remote image URL is accepted through the chooser. Selecting Original explicitly overrides a legacy filename map for that subscription and leaves the original upload unchanged.

My Icons is a per-account reusable library capped at 100 images and 32 MiB of normalized bytes. Upload accepts PNG, JPEG, WebP, and SVG. The server checks authentication, CSRF, actual MIME/decoder result, byte size, pixel dimensions, and ownership. Raster uploads are decoded and re-encoded, stripping metadata. SVG uploads are accepted only through a strict element/attribute allow-list with DTD, external references, CSS URLs, scripts, events, animation, and embedded content rejected. The image adds Alpine's [`rsvg-convert`](https://pkgs.alpinelinux.org/packages?name=rsvg-convert&branch=v3.24) package to both architecture builds and records its exact package version; an unprivileged process rasterizes accepted SVG within a five-second timeout, 128 MiB memory limit, and 1024 px output bound. Its input is a local temporary file with no permitted external references. GD decodes and re-encodes the rasterized output. Malicious SVG samples covering entities, remote references, embedded content, oversized paths, and renderer timeout are release tests. No SVG submitted through this UI is stored or served raw; the existing admin-managed local SVG mount is a separate legacy path. The normalized image is at most 1024 px on either side and 512 KiB after encoding; the upload request is limited to 2 MiB. Identical normalized images in one account reuse the existing library entry by content hash. Quota errors show the current use and the option to delete unused images. A smaller raster source can be used with a visible low-resolution warning; it is never presented as newly sharp. Invalid input changes neither the current selection nor the subscription.

The built-in SVGs stay in the image. User-uploaded normalized images are held as BLOBs in a Dial-owned SQLite table in the existing database volume, rather than being placed in Wallos's URL-readable Logo directory. A session- and owner-checked image endpoint serves them with the correct image MIME type, `nosniff`, and `no-store`. The service worker treats this endpoint as network-only. This protects the new library; it does not change Wallos's existing URL-readable original Logo uploads. Library images can be deleted when no subscription uses them; deleting a subscription removes its preference, while reusable library images remain until the user deletes them. Deleting an account removes its preferences and library images.

Uploading to My Icons is an independent, explicitly confirmed library action. A successful upload remains in My Icons if the user later cancels the subscription form or that form fails; it can be reused or deleted there. The Wallos add/edit endpoint then saves the subscription and its selected icon preference in one SQLite transaction. It currently returns no new subscription ID, so a separate client-side preference request cannot give reliable all-or-nothing behavior. The 1.0 overlay of this endpoint starts from Wallos 5.8.3 and retains its ownership checks. Any original Wallos Logo and variant upload is validated and staged first. Within the database transaction the staged files move to their final names before commit; move failure rolls back, and commit failure removes the new files. Only after a successful commit may an old Logo be deleted, with failed old-file cleanup retried later rather than risking the saved subscription. The implementation plan must test each failure point so no committed row references a missing new file and the prior Logo survives an aborted edit. Invalid preference or foreign asset ID fails the subscription operation with a visible error; it must not leave a newly created subscription with an unintended icon state. Cloning a subscription copies its icon preference and references the same owned My Icons asset, without duplicating image bytes; later edits to either subscription remain independent.

## Data and rendering boundaries

A Dial migration with a `dial_` name creates `dial_icon_assets` and `dial_subscription_icons` without occupying a numbered upstream migration. It is idempotent and runs after the upstream migrations. `dial_icon_assets` contains account ID, label, normalized image MIME and bytes, content hash, and creation time. `dial_subscription_icons` is unique by `(user_id, subscription_id)` and records source (`original`, `catalog`, or `asset`), the allowed catalog key or owned asset ID, presentation, treatment, scale, and update time. No row means automatic legacy-map-or-original behavior. SQLite `AFTER DELETE` triggers clean preferences on subscription deletion and both tables on account deletion, including when the database is used after rollback to 0.1.1; the current Wallos connection does not enable foreign-key enforcement.

Every icon write validates both the subscription and referenced asset against the session's `user_id`. Read paths use one resolver, which returns a trusted catalog URL, an authenticated asset URL, the legacy local SVG, or the original Logo in that order according to the saved preference. The resolver never accepts a user-provided path. It is used by the dashboard payment rows and other dashboard widgets, grouped and ungrouped subscription cards, the details/edit response, and any statistics view that displays a service icon. The rendered mark is decorative where the adjacent service name already identifies the item.

Old Wallos/Dial images ignore the new tables on rollback, so the original Logo reappears. Reinstalling Dial 1.0 restores the saved selection. Docs must explain that SQLite backups now include My Icons, while existing Wallos uploaded Logos remain in their separate mounted volume. Upgrade and restore tests cover both volumes.

## Category manager

`categories.php` is a dedicated Dial page reached from the subscriptions toolbar and linked from settings. It reads the existing per-account `categories(id, name, order, user_id)` table; no second category table is created. The page shows every category, its total subscription count (including inactive and one-time items), direct rename, add, keyboard and drag sorting, delete of an unused category, and a Merge action for a category in use. Controls and feedback use English, Simplified Chinese, or Traditional Chinese according to the account's Dial language. An account with no subscriptions can opt into the Dial starter set (AI, Infra, Domains, Media) after seeing a preview. It adds missing names; the user separately selects the exact ID/name rows of empty, deletable categories to remove. Wallos has no reliable default-category marker, so no category is selected for deletion automatically. Any upstream-protected fallback category such as `id=1` remains. The starter set does not change other accounts or run automatically.

Mutations require login, POST, CSRF, `user_id` checks, and `DEMO_MODE` rejection. Names are length- and control-character-limited. They retain Wallos's entity-escaped storage convention: the editor decodes one stored layer for its input, a save applies the existing `validate()` once, and new Dial HTML output decodes that stored layer and escapes it at the output boundary. A historically multiply encoded value is shown for manual correction rather than silently decoded to a potentially different literal name. The main Dial grouping, category filters, manager inputs, and existing Settings category inputs must show a newly saved `AI & Tools` correctly after repeated saves and reloads. The existing `endpoints/categories/category.php` is hardened so Settings and the new manager share safe add, rename, sort, and empty-delete behavior; a separate Dial endpoint implements transactional merge. Its `add` action accepts and validates an optional nonempty name for the manager, while retaining the old unnamed `Category` insertion for Settings. The relevant Settings input is updated to avoid double encoding, with its upstream file added to the compatibility hash gate.

Merge runs in one `BEGIN IMMEDIATE` SQLite transaction: confirm distinct source and target owned by the account; move only that account's subscriptions to the target; delete exactly one source category; renumber order; commit. Any failed check or database operation rolls back. The global `id=1` category retains upstream's deletion guard; it is not assumed to be every account's first category. No account may end with zero categories. Sorting also uses `BEGIN IMMEDIATE`; the submitted payload contains every movable category ID for that account exactly once, excluding `id=1` only when that account owns it. The server checks that set against the database, keeps `id=1` first when present, writes contiguous order, and rolls back on any failed update. Subscription creation and editing both reject a category ID not owned by the account. On return from the manager, the subscriptions page fully refreshes categories, filters, groups, and form choices, including after a browser back/forward-cache restore; statistics read the committed state on their next view.

## Wallos 5.8.3 upgrade and cache behavior

The Docker base is pinned to the reviewed Wallos 5.8.3 multi-architecture digest. Every overridden upstream file is checked against the new base before copying, and the compatibility manifest is regenerated only after reviewing its diff. Dial's notification override incorporates all eleven upstream household ownership checks while retaining the 0.1.1 email templates. The 5.8.2 server-side SSO-only and subscription foreign-key ownership fixes must be present in the built image and tested. No live private database is used for these tests.

The service worker static cache key includes both the Wallos and Dial versions. Dial's CSS, JavaScript, and built-in icon assets are handled consistently with the updated cache; the authenticated custom-icon endpoint is excluded from offline storage. Tests use a browser already controlled by the old 0.1.1 worker and a browser controlled by 1.0, then update the image to verify the current assets load. Query parameters alone are not accepted as proof because Wallos 5.8.3 matches cached static assets while ignoring the query string.

## Demo, documentation, and release

The public Demo continues to run the installable image with fictional subscriptions and remains read-only at the reverse proxy and application mutation endpoints. It shows the built-in icons and categories. Its reverse proxy permits a read-only GET of the manager page; Demo Mode hides or disables editing controls and explains that changes require a personal installation. The icon chooser is likewise shown only as a non-editing preview in the Demo. The new mutation endpoints reject Demo Mode even if the proxy is misconfigured. Documentation and actual application captures demonstrate the writable flows on an isolated local instance. The Demo never mounts maintainer uploads, private SVGs, a private database, or the private filename map.

English and Simplified-Chinese READMEs, install/upgrade/rollback guides, release notes, product pages, and the Demo description are updated for 1.0.0 and Wallos 5.8.3. Actual application captures show the icon chooser and category manager, alongside the existing before/after theme comparison, for future posts and video planning. Historical requirements that say no brand SVGs ship are revised to describe the reviewed public catalog and private exclusion. Installation retains the versioned GHCR tag and loopback-bound Compose example. Future upstream compatibility is never implied without a tested Dial image.

The implementation is prepared and verified locally first. A separate reviewed release decision covers pushing `main`, creating `v1.0.0`, publishing both GHCR architectures and GitHub Release, and updating only the public Demo. The private Wallos deployment and community posts are separate actions.

## Acceptance evidence

The 1.0 candidate is ready for release review only when the following evidence exists:

1. **Package/privacy:** a clean source checkout builds on Wallos 5.8.3; the nine reviewed public candidates have per-asset provenance; private SVG assets, private filename maps, user data, and secrets are absent from source, image layers, docs assets, and release archive.
2. **Fresh/upgrade/rollback:** a fresh database migrates and serves the app; a disposable copy of a 0.1.1 database preserves subscriptions, category assignments, original Logos, notification settings, and mail behavior on upgrade; the old image can read and write that copy again with original Logos visible, including a normal subscription add/edit/delete while Dial triggers remain installed; re-upgrade restores surviving preferences without reviving deleted ones; SQLite integrity checks pass in each state.
3. **Icon operation:** users can choose catalog and library icons, upload each accepted format, edit presentation, restore Original, delete an unused library icon, and see a consistent result across all listed views after reload and new login. Bad image, oversized image, missing catalog key, and missing asset produce a safe fallback or clear error without partial writes.
4. **Access control:** two-account tests reject foreign subscription, category, library-asset, payment, and household IDs. Unauthenticated, missing-CSRF, and Demo writes are rejected. A user cannot fetch another user's icon image. Account and subscription deletion clean dependent Dial state.
5. **Category operation:** add, rename, keyboard/drag sort, delete empty, transactional merge, last-category guard, default-ID guard, `AI & Tools` display, and optional starter set are verified. Grouping, search, filters, statistics, and forms update after each committed change.
6. **Upstream and existing features:** SSO-only direct login is denied; subscription ownership checks and all eleven notification household checks are present. Add/edit/clone/delete subscriptions, dashboard, calendar, stats, settings, language switching, search, five styled email flows, and other notification channels are exercised in an isolated environment.
7. **Presentation/cache/platform:** desktop widths and browser zoom are visually checked in English, Simplified Chinese, and Traditional Chinese; focus and keyboard use are checked; an old service worker loads 1.0 assets; both amd64 and arm64 images build and start. The public Demo passes anonymous read and write-block checks after its update.

Tests, syntax checks, a green image build, and a healthy container each prove only their covered part of this list. The release decision uses the complete evidence set and records any remaining limitation explicitly.
